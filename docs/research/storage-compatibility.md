## Уточнение от 06.11.2026: содержимое в регистре `ХранилищеФайлов`

Проверка `hlev` показала, что содержимое файлов фактически хранится не только в реквизите `ФайлХранилище`:

| Файл | Тип хранения | `Размер` | Запись в `РегистрСведений.ХранилищеФайлов` | Размер в регистре |
|---|---|---:|---|---:|
| `КомандировкаПрисоединенныеФайлы` → `2` | `ВИнформационнойБазе` | 77 236 | есть | 77 236 |
| `КомандировкаПрисоединенныеФайлы` → `photo_2026-11-02_15-18-51` | `ВИнформационнойБазе` | 252 281 | есть | 252 281 |
| `КомандировкиСотрудниковПрисоединенныеФайлы` → `rclone-v1.75.2-windows-amd64` | `ВИнформационнойБазе` | 31 634 900 | есть | 31 634 900 |

У всех трёх записей реквизит `ФайлХранилище` не `NULL`, но полезных данных в нём нет — иначе прежняя версия обработки, читавшая только этот реквизит, не пропускала бы их. Содержимое лежит в `РегистрСведений.ХранилищеФайлов` → `Справочник.ХранилищеДвоичныхДанных` (`Размер`, `Хеш`, `ДвоичныеДанные` типа `ХранилищеЗначения`).

Штатный механизм чтения — `РаботаСФайлами.ХранилищеФайлаИзИнформационнойБазы(ФайлСсылка, ПолучениеФайлаИзАрхива = Ложь)`: для типа `ВИнформационнойБазе` он выбирает двоичные данные из регистра, для остальных типов — из внешнего места хранения (не используется). Обработка вызывает его и оставляет резервный путь через `ФайлХранилище` для старых данных.

Вывод: фильтр по `ТипХраненияФайла` и чтение через БСП обязательны; проверка «`ФайлХранилище` не `NULL`» недостаточна.

## Справочники `*ПрисоединенныеФайлы`

В обеих базах есть, например, `Справочник.ТранспортноеСообщениеПрисоединенныеФайлы` и `Справочник.ПерепискаСКонтролирующимиОрганамиПрисоединенныеФайлы`. Структура (одинаковая по проверенным объектам):

- `ВладелецФайла` — конкретный тип владельца;
- `ФайлХранилище`, `ТипХраненияФайла`, `Том`, `ПутьКФайлу`, `Размер`, `Расширение`, `ИсходноеИмяФайла`, `ХранитьВерсии`, `ПодписанЭП`;
- **версий нет** — содержимое хранится в самом элементе справочника.

Эти объекты обрабатываются существующим сценарием только для трёх жёстко перечисленных видов. Новый режим обнаруживает все справочники, имя которых содержит `ПрисоединенныеФайлы` и есть реквизиты `ФайлХранилище` и `ТипХраненияФайла`.

## Тома хранения

`Справочник.ТомаХраненияФайлов` (обе базы): `ВидТомаХраненияФайлов`, `СпособХраненияФайлов`, `ПолныйПутьWindows`, `ПолныйПутьLinux`, `ИмяХранилищаДвоичныхДанных`, `МаксимальныйРазмер`. Для режима не используются: файлы в томах и хранилищах двоичных данных блокируются.

## Вывод о механизме

1. Штатный файловый архив БСП — глобальная подсистема: перенос выполняется регламентным заданием по настройкам, файлы помечаются `ДатаПереносаВАрхив`, восстановление выполняет сама подсистема при обращении. Для выборочного архивирования конкретных файлов пользователем из внешней обработки он не подходит и требует изменения настроек базы.
2. Содержимое `ВИнформационнойБазе` читается штатным механизмом БСП `РаботаСФайлами.ХранилищеФайлаИзИнформационнойБазы`, то есть из `РегистрСведений.ХранилищеФайлов` / `Справочник.ХранилищеДвоичныхДанных`, с резервным путём через реквизит `ФайлХранилище`. Это единственный тип, который освобождает место в информационной базе при очистке, но очистка должна удалять и запись регистра (`РегистрСведений.ХранилищеФайлов.УдалитьДвоичныеДанные`), а не только реквизит.
3. Для `ВТомахНаДиске` очистка реквизита не освобождает диск и требует удаления файла по пути тома; для хранилищ двоичных данных содержимое общее (дедупликация). Оба случая небезопасны без отдельного исследования и блокируются.
4. Проверка типа выполняется по `ТипХраненияФайла` в запросах очереди и повторно перед чтением содержимого; неподдерживаемые единицы в очередь не попадают.
