# Безопасность очистки: подтверждённые механизмы и необходимые испытания

Статус: исследование; очистка и восстановление **включены** в сборке 06.11.2026.
Реализованы транзакции, управляемые блокировки, привязка манифеста к базе и
области. Основной цикл (архив → проверка → очистка → восстановление) выполнен
в `bgu`, область 25, на двух файлах. Остаются неподтверждёнными конкурентные
сценарии двумя сеансами и поведение всех подписок конкретных конфигураций.
Источники: `1S-Gate`, конфигурации `bgu` и `hlev`, БСП 3.1.12.297.

## Подтверждённые факты

1. В обеих конфигурациях `ОбщийМодуль.РаботаСФайламиСлужебный.Модуль`, строка 926,
   блокирует `Справочник.ВерсииФайлов` по полю `Владелец` ссылкой на файл.
   В `Справочник.ВерсииФайлов.МодульМенеджера`, строка 173, применяется
   блокировка этого справочника по полю `Ссылка`. Следовательно, выбор только
   одной из этих блокировок без проверки пересечения с типовыми операциями
   недостаточен для вывода о конкурентной безопасности.
2. В обеих конфигурациях `РегистрСведений.ХранилищеФайлов.МодульМенеджера`,
   строка 447, содержит блокировку `Справочник.Файлы` по полю `Ссылка`.
   Необходимо установить порядок блокировок файла и версии, совместимый с
   типовыми обработчиками, и проверить его двумя параллельными сеансами.
3. В обеих конфигурациях `СтандартныеПодсистемыСервер.ИдентификаторИнформационнойБазы()`
   является экспортной функцией. В её теле присутствует запись константы
   `ИдентификаторИнформационнойБазы`, а не только чтение. Кроме того, константа
   может быть скопирована вместе с базой. Самого этого значения недостаточно
   для доказательства, что архив создан именно в текущем экземпляре базы.
4. В обеих конфигурациях `РаботаВМоделиСервиса.ЗначениеРазделителяСеанса()`
   найден как экспортная функция; при выключенном разделении возвращает 0, при
   включённом без установленного разделителя выбрасывает исключение. Для `bgu`
   пользователь подтвердил область данных 25.

## Уточнение о смене текущей версии

В обеих выгрузках найден `РаботаСФайламиСлужебный.ОбновитьВерсиюВФайле`
(строки 5747–5788; файлы модулей в `bgu` и `hlev` побайтно совпадают).
Процедура начинает транзакцию, устанавливает управляемую блокировку карточки
по `Ссылка`, вызывает `ЗаблокироватьДанныеДляРедактирования`, перечитывает
карточку, меняет `ТекущаяВерсия` и записывает её. Следовательно, блокировка
только строки версии недостаточна для обоснования корректности проверки
текущей версии и обновления размера её карточки.

В `ПометитьНаУдалениеВерсииФайла` (строки 906–942) блокировка версий по
`Владелец` берётся отдельно, а в `ОбработатьВерсиюФайла` модуля менеджера
версий (строки 167–219) — по `Ссылка`. Эти примеры не устанавливают общего
порядка захвата обеих блокировок вместе с карточкой и не доказывают их
пересечение с неявными блокировками записи. Перед реализацией следует отдельно
проследить вызывающие операции и обработчики записи, а затем проверить
реальное ожидание и взаимоблокировки двумя сеансами на стенде.

Текущая `ОбновитьРазмерФайла` в обработке возвращается без ошибки, если
карточка не найдена. Транзакции вокруг существующего кода недостаточно:
этот случай необходимо отклонять, а проверку владельца и текущей версии
проводить после получения подходящих блокировок. **В сборке 06.11.2026
исправлено:** отсутствие карточки — исключение и откат; блокировки ставятся до
повторной проверки содержимого. Порядок блокировок подтверждён только по
исходному коду, не экспериментом.

## Реализованные меры (06.11.2026)

1. Очистка и восстановление работают с `РегистрСведений.ХранилищеФайлов`
   (`УдалитьДвоичныеДанные`, `ЗаписатьДвоичныеДанные`), а не с реквизитом
   `ФайлХранилище`. Реквизит очищается как совместимый след старого способа
   хранения; чтение сначала идёт через
   `РаботаСФайлами.ХранилищеФайлаИзИнформационнойБазы`, затем — резервно через
   реквизит.
2. Каждая запись обрабатывается в отдельной транзакции:
   `НачатьТранзакцию` → блокировки → повторная проверка типа и хеша →
   запись регистра и карточки → контрольное чтение → `ЗафиксироватьТранзакцию`;
   при ошибке — `Если ТранзакцияАктивна() Тогда ОтменитьТранзакцию()`.
3. Управляемые блокировки ставятся до повторной проверки: версия (для версии),
   карточка `Справочник.Файлы` (для версии), запись
   `РегистрСведений.ХранилищеФайлов` по `Файл`.
4. Манифест `formatVersion = 2` содержит `infobaseId`
   (`СтандартныеПодсистемыСервер.ИдентификаторИнформационнойБазы()`) и
   `dataArea` (`РаботаВМоделиСервиса.ЗначениеРазделителяСеанса()`). Манифест без
   идентичности, из другой базы или области отклоняется; изменяющие операции
   дополнительно требуют `completed` и `verified`.
5. Для исторической версии запись выполняется с
   `ДополнительныеСвойства.Вставить("КонвертацияФайлов", Истина)`. Это
   предотвращает перенос реквизитов исторической версии в карточку текущего
   файла подпиской `ВерсииФайловПриЗаписи`, но одновременно пропускает
   `ОбновитьСостояниеОчередиИзвлеченияТекста`. Для очищенного/восстановленного
   содержимого это приемлемо: текст извлекается из содержимого, а не из факта
   записи; после восстановления поиск по тексту потребует отдельной индексации.

## Остаточный риск взаимоблокировки

Порядок блокировок обработки: версия/карточка → запись регистра
`ХранилищеФайлов` → `Справочник.ХранилищеДвоичныхДанных` (неявно, внутри
`УдалитьДвоичныеДанные`/`ЗаписатьДвоичныеДанные`). Типовой
`ЗаписатьДвоичныеДанные` блокирует `Справочник.ХранилищеДвоичныхДанных` по
хешу **до** удаления и записи регистра. Если параллельный сеанс пишет тот же
файл, возможна взаимоблокировка; платформа откатит одну транзакцию. Обработка
поймает ошибку, откатит свою транзакцию и запишет строку «Ошибка». Потери
данных при этом не ожидается, но автоматического повтора нет. Проверка двумя
сеансами остаётся обязательной.

## Подписка при записи исторической версии

Подписка `СкопироватьРеквизитыВерсииФайловВФайл` имеет источник
`СправочникОбъект.ВерсииФайлов`, событие `ПриЗаписи` и вызывает
`РаботаСФайламиСлужебный.ВерсииФайловПриЗаписи`. В обеих выгрузках XML
подписки и модуль объекта `ВерсииФайлов` побайтно совпадают; сам общий
модуль ранее также сравнен побайтно.

В обработчике подписки (общий модуль, строки 10193–10261) при отличии
размера или другого перечисленного реквизита версия блокирует карточку
владельца и записывает в неё размер, расширение, том, путь и другие реквизиты
версии. Поле `ТекущаяВерсия` читается на строке 10212, но в условии
строк 10214–10219 сравнения с записываемой версией нет. Поэтому запись
исторической версии в текущей реализации обработки **может изменить
реквизиты карточки текущего файла**; это вывод по исходному коду, а не
результат эксперимента в платформе.

Объектный обработчик `ПередЗаписью` версии (строки 13–85) также читает
текущую версию и пометку удаления владельца. Флаги `КонвертацияФайлов` и
`ОбменДанными.Загрузка` меняют поведение обработчиков, но использовать их
как готовое решение нельзя без анализа всех подписок и побочных эффектов:
например, загрузка вызывает отдельный `ЗаписатьДанныеФайлаВРегистрПриОбмене`.

Испытание должно отдельно создать две версии с различными размерами и
реквизитами, очистить и восстановить неактуальную версию, убедившись, что
текущая версия и вся карточка остаются неизменными. Также необходимо проверить
откат побочных записей подписок при принудительной ошибке и конкуренцию
типовой записи версии с захватом карточки. До этих проверок просто окружать
существующие вызовы `Записать()` транзакцией небезопасно.

## Дополнительные побочные действия при записи

Проверены XML подписок, в которых `CatalogObject.ВерсииФайлов` или
`CatalogObject.Файлы` перечислены непосредственно (это **не** полный аудит
подписок по определяемым типам и расширениям). В БГУ на `BeforeWrite`
найдены обработчики регистрации обменов `Полный`, `ПоОрганизации` и
`АвтономнаяРабота`; в ЗКГУ — `ОбменВРаспределеннойИнформационнойБазе` и
`АвтономнаяРабота`. `ОбменДаннымиСобытия.МеханизмРегистрацииОбъектовПередЗаписью`
в ЗКГУ (строки 50–68) может пропустить регистрацию при специальном свойстве,
но в автономном рабочем месте обработчик ЗКГУ отдельно добавляет главный узел
в получатели. Нельзя считать установку одного свойства универсальным способом
исключить передачу технического удаления содержимого в другие базы.

Подписка `ВерсииФайловПриЗаписи` вызывает
`ОбновитьСостояниеОчередиИзвлеченияТекста`; если выполнены условия разделения
и подсистемы, через `РаботаСФайламиСлужебныйВМоделиСервиса` производится
запись набора регистра `ОчередьИзвлеченияТекста` с отбором по области и
источнику (строки 20–44). Возврат из подписки по служебному свойству
`КонвертацияФайлов` пропускает не только копирование реквизитов карточки, но
и этот вызов. Применимость свойства для архивации и последствия для поиска и
обмена не доказаны; устанавливать его в рабочем коде без исследования нельзя.

Приёмка транзакционной операции должна проверять не только размеры, хеши и
текущую версию, но и записи очереди извлечения текста и регистрации изменений
в обменах — до операции, после фиксации и после принудительного отката.
Нужно отдельно проверить разделённый сеанс и автономное рабочее место.
Существующий `tests/isolation/historical_rollback.bsl` сравнивает только
количество видимых записей очереди извлечения по тестовой версии. Это не
сравнение содержимого регистра, не доказательство срабатывания подписки и не
проверка регистрации обмена; сценарий не является достаточным тестом операции.

## Минимальные приёмочные испытания на изолированных копиях

- Ошибка при записи карточки после записи версии: обе записи откатываются;
  исходные содержимое и размер совпадают с состоянием до операции.
- Два сеанса: один изменяет содержимое во время очистки и во время
  восстановления. Операция либо ждёт блокировку и повторно проверяет хеш,
  либо завершается конфликтом без потери нового содержимого.
- Смена текущей версии и владельца в конкурентном сеансе: ни одна чужая
  версия не очищается и размер текущей карточки не становится неверным.
- Другая база с той же конфигурацией и совпадающими UUID, в том числе клон
  с тем же значением константы: операция изменения отклоняется.
- Другая область той же разделённой базы и неустановленный разделитель:
  операция изменения отклоняется до первой записи.
- Разрыв связи, ошибка хеширования, нехватка прав и откат транзакции: архив
  остаётся пригодным для восстановления, частичных изменений в ИБ нет.

Это критерии, а не результаты испытаний. Для испытания разделения нужна
отдельная тестовая разделённая ИБ с минимум двумя областями и доступными
тестовыми сеансами; рабочие базы для записи использовать нельзя.
