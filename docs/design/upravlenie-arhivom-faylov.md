# Управление архивом присоединённых файлов — отдельная обработка

Статус: дизайн согласован 06.11.2026; реализован 07.11.2026
(`build/УправлениеАрхивомПрисоединенныхФайловОчисткаИВосстановление.epf`).
Изменяющие проверки на копии базы ещё не выполнялись — чек-лист
`docs/testing/upravlenie-arhivom-acceptance.md`.

## Что и зачем

Сценарий «все присоединённые файлы» (анализ → архивирование → проверка →
очистка содержимого → восстановление) сейчас живёт внутри
`СозданиеАрхиваДокументооборота.epf` отдельной формой. Эта обработка решает
другую задачу — подготовку архива документооборота для 1С-Отчётности, и
посторонняя форма усложняет её сопровождение.

Нужна самостоятельная обработка с тем же сценарием, но с тремя улучшениями:
видимый прогресс, штатная отметка «файл в архиве» после очистки и отбор по
периоду.

## Цели

1. Новая внешняя обработка
   `УправлениеАрхивомПрисоединенныхФайловОчисткаИВосстановление.epf` содержит
   полный цикл: анализ, архивирование, проверку архива, очистку содержимого,
   восстановление.
2. Исходная `СозданиеАрхиваДокументооборота.epf` сохраняет только сценарий
   1С-Отчётности: форма «Все файлы», её команда и кнопка удаляются.
3. Прогресс-бар виден при всех пяти длительных операциях.
4. Очищенный файл получает штатную отметку БСП «перенесён в архив»;
   восстановление её снимает.
5. Отбор файлов по одному периоду `СтандартныйПериод`: дата документа-владельца,
   а если её нет — дата создания файла.

## Не-цели

- Расширение конфигурации и колонка «Архивный» в стандартном списке
  присоединённых файлов. Отметка видна в форме версии файла и в сообщении при
  открытии, но не в списке документа.
- Тома на диске, внешние и встроенные хранилища двоичных данных, файловый
  (zip) архив БСП.
- Автоматический перенос в файловый архив и обратно.
- Сохранение каталога архива и периода между запусками.
- Совместимость манифестов с прежней сборкой (см. «Манифест»).
- Автоматический повтор записи при взаимоблокировке.

## Анти-цели

Считать работу неудачной, если:

- содержимое очищено, а архив не проверен или неполон;
- изменена запись, которой нет в манифесте;
- восстановленный файл не открывается из-за оставленной отметки архива;
- после очистки карточка, версия или связь с владельцем потеряны;
- обработка тронула файл с типом хранения, отличным от «В информационной базе».

## Ограничения и проверенные факты

Проверено по `/srv/dumps/bgu` (БСП 3.1.12.297) и по текущим исходникам.

1. **Чтение не зависит от отметки, а распаковка — зависит.**
   `РаботаСФайлами.ПолучитьТекстЗапросаДляПолученияДвоичныхДанныхФайла` для типа
   «В информационной базе» всегда читает `РегистрСведений.ХранилищеФайлов`, в
   том числе при `ПолучениеФайлаИзАрхива = Истина`. Но вызывающий код
   (`РаботаСФайлами.ДанныеФайла`, строка 278) при этом признаке дополнительно
   вызывает `РаботаСФайловымАрхивомСервер.ДвоичныеДанныеФайлаИзвлеченногоИзZipАрхива`.
   Значит: без содержимого — корректное сообщение «файл находится в файловом
   архиве», с содержимым — исключение «Ошибка при извлечении файла из
   Zip-архива».
2. **Отметку читает `ФайлПеренесенВФайловыйАрхив`** по реквизиту
   `ДатаПереносаВАрхив`: для `СправочникСсылка.ВерсииФайлов` — на версии, для
   `СправочникСсылка.Файлы` — на текущей версии, для прочих типов — в
   `РегистрСведений.СведенияОФайлах` по полю `Файл`.
3. **Плановые задания БСП отметку не ломают.** Перенос в файловый архив
   выбирает только записи с `ДатаПереносаВАрхив = ДатаВремя(1,1,1)`;
   восстановление из zip — только типы `ВТомахНаДиске` и
   `ВоВнешнемХранилищеДвоичныхДанных` (`ИНАЧЕ ЛОЖЬ`). Файлы «В информационной
   базе» с отметкой оба задания пропускают.
4. **Иконка архива** рисуется в форме `Справочник.ВерсииФайлов.Форма.ВерсииФайла`
   по условию `ДатаПереносаВАрхив = ДатаВремя(1,1,1)` (колонка
   `НомерКартинкиЭтоАрхив`).
5. **Подписка `СкопироватьРеквизитыВерсииФайловВФайл`** копирует реквизиты версии
   в карточку при записи, если в `ДополнительныеСвойства` нет
   `КонвертацияФайлов` или `ПереименованиеФайла`. Текущий код уже использует
   `КонвертацияФайлов` для исторических версий.
6. **`СведенияОФайлах` — независимый регистр сведений** с измерением `Файл` и
   ресурсами, включая `ДатаПереносаВАрхив` и `УсловноПеренесенВАрхив`. Штатный
   способ записи одного поля — `СоздатьМенеджерЗаписи`, `Файл = ...`,
   `Прочитать()`, изменить, `Записать()`; прямая запись только двух полей
   обнулила бы остальные ресурсы.
7. **`УсловноПеренесенВАрхив = Истина` означает «условно в архиве»** и
   используется заданиями БСП как признак кандидата на очистку. Выставлять его
   нельзя: только `Ложь`.
8. **У файлов без версий (`ХранитьВерсии = Ложь`, пустая `ТекущаяВерсия`)**
   `ФайлПеренесенВФайловыйАрхив` берёт ветку `СправочникСсылка.Файлы` и читает
   `ТекущаяВерсия.ДатаПереносаВАрхив`; у `Справочник.Файлы` нет собственного
   реквизита `ДатаПереносаВАрхив`. Отметить такой файл штатно невозможно.
   В `bgu`, область 25, таких файлов нет (2 файла, оба с версиями).
9. **Платформа поддерживает `СтандартныйПериод`**: тип формы
   `<v8:Type>v8:StandardPeriod</v8:Type>`, элемент `InputField`; используется в
   `bgu` в 2347 формах. Свойства значения: `ДатаНачала`, `ДатаОкончания`,
   `ВариантПериода` (не `НачалоПериода`/`КонецПериода` — проверено на
   `Обработки.ОбменССистемойУчетаИмущества.Форма`: `Период.ДатаНачала`).
10. **`ФормаПрогресс` исходной обработки занята формой «Основная»** (архивация
    документооборота). Переносить её нельзя — нужна собственная реализация в
    новой обработке.
11. **`configName` манифеста — это `Метаданные.Имя` внешней обработки**, а не имя
    конфигурации; `configVersion` — `Метаданные.Версия` обработки. Пример в
    `docs/design/all-attached-files.md` с именем конфигурации неверен.

## Подходы

**A. Встроенный прогресс на рабочей форме (выбран).**
Индикатор и подпись — элементы самой формы, видны только во время операции.
Логика переносится копией, серверный цикл очистки разбивается на вызовы по
одной записи. Одно окно, прогресс у всех операций, нет обвязки `Оповестить`.
Плата: очистка перестаёт быть одним серверным вызовом — вместо этого N вызовов
по записи; каждая запись и так шла в отдельной транзакции.

**B. Отдельное окно прогресса.**
Копия `ФормаПрогресс` внутри новой обработки, обновление через `Оповестить`.
Минимум изменений в проверенной логике, но лишнее окно, которое нужно гасить, и
та же обвязка для трёх операций, где прогресса сейчас нет. Отклонено.

Других вариантов нет: внешние обработки не разделяют код, поэтому «вынос» —
это копия модуля формы в новый объект.

## Устройство

### Состав исходников

```
src/УправлениеАрхивомПрисоединенныхФайловОчисткаИВосстановление.xml
src/УправлениеАрхивомПрисоединенныхФайловОчисткаИВосстановление/
  Ext/ObjectModule.bsl                 — пустой (логика отчётности не нужна)
  Forms/СписокФайлов/Ext/Form.xml
  Forms/СписокФайлов/Ext/Form/Module.bsl
```

- `DefaultForm` — `СписокФайлов`; других форм нет, обработка открывается сразу
  на рабочей форме.
- `Метаданные.Версия` — недоступно: платформа 8.3.27 не принимает свойство
  `<Version>` у `ExternalDataProcessor` («Свойство Version не входит в состав
  объекта метаданных ExternalDataProcessor»), поэтому `configVersion` в
  манифесте — пустая строка. Ни один потребитель манифеста его не требует.
- Сборка и выгрузка — теми же командами `1cv8 DESIGNER`, что и текущая
  обработка; добавить скрипт `build/` или строку в `README.md`.

### Форма

Переносится из `Forms/ВсеФайлы` без изменения назначения. Состав:

- реквизиты: `КаталогАрхива`, `Период` (`СтандартныйПериод`), `Сеанс`,
  `ТолькоТекущиеВерсии`, `ТаблицаРезультата`, `ТекстЛога`, `ОчередьФайлов`,
  `МанифестШапка`;
- новые реквизиты прогресса: `Прогресс` (Число), `ПрогрессНадпись` (Строка),
  `ПрогрессВидимость` (Булево);
- группа `ГруппаПрогресса` внизу формы: только полоса `Прогресс` и подпись
  `ПрогрессНадпись`, видимость группы — по `ПрогрессВидимость`;
- команды: `Анализ`, `Архивировать`, `ПроверитьАрхив`, `Очистить`,
  `Восстановить`, `ПоследнийСеанс`, `ПроверитьКаталог`.

Поле периода — отдельный `InputField` в верхней части формы, рядом с каталогом
архива, **вне** `ГруппаПрогресса`: его заполняют до запуска операции, а группа
прогресса скрыта до начала работы. Видимостью периода `ПрогрессВидимость` не
управляет, иначе поле исчезло бы ровно тогда, когда нужно. Изменение периода
пересчитывает статистику только по команде «Анализ», без автопересчёта.

### Период

Правило эффективной даты (применяется только когда период задан):

1. Если `ВладелецФайла` заполнен и у его метаданных есть реквизит `Дата` —
   берётся значение этого реквизита (дата документа).
2. Иначе — `ДатаСоздания` файла (`Файлы.ДатаСоздания` или одноимённый реквизит
   присоединённого справочника, если он есть).
3. Если ни того, ни другого нет — запись не проходит отбор и попадает в лог
   одной строкой с причиной.

Если период не задан, даты не вычисляются вовсе: в очередь попадают все файлы,
включая записи без владельца и без даты создания. Это сохраняет поведение
текущей сборки и не превращает правило 3 в скрытый предварительный фильтр.

Границы включают последний день: сравнение идёт с
`НачалоДня(Период.ДатаНачала)` и `КонецДня(Период.ДатаОкончания)`.

Незаполненный период (`ДатаНачала` и `ДатаОкончания` равны `0001-01-01`)
означает «все файлы» — поведение текущей сборки.

Даты владельцев кешируются в `Соответствие` по ссылке владельца в пределах
одного построения очереди: у одного документа обычно много версий. Поиск в
кеше — `Получить`, а не `Найти`: метода `Найти` у `Соответствия` нет (в рантайме
8.3.27 — «Метод объекта не обнаружен (Найти)»). Так как `Получить` возвращает
`Неопределено` и для отсутствующего ключа, и для сохранённого `Неопределено`,
отсутствие даты владельца кешируется маркером `Дата(1, 1, 1)`, а `Неопределено`
в кеш не попадает никогда.

Применение:

- анализ и построение очереди (`ВыполнитьАнализНаСервере`,
  `Архив_ДобавитьВерсии`, `Архив_ДобавитьФайлыБезВерсий`,
  `Архив_ДобавитьПрисоединенные`) — с отбором;
- проверка архива, очистка и восстановление работают **по манифесту сеанса**,
  а не по текущему периоду. Период влияет только на состав нового сеанса;
  смена периода не расширяет и не сужает уже созданный сеанс. Это решение
  исполнителя: иначе после смены периода нельзя было бы ни проверить, ни
  очистить, ни восстановить уже заархивированное.

В манифест пишутся `periodStart` и `periodEnd` — для разбора инцидентов.

### Прогресс

Клиентские процедуры формы:

- `НачатьПрогресс(Заголовок)` — `ПрогрессВидимость = Истина`, `Прогресс = 0`;
- `ОбновитьПрогресс(Обработано, Всего, Текст)` — процент и подпись;
- `ЗавершитьПрогресс()` — `ПрогрессВидимость = Ложь`.

Вызовы:

- анализ — после каждого `Анализ_ШагНаСервере` (один шаг — один справочник,
  перечень шагов даёт `Анализ_ИсточникиНаСервере`); итоги —
  `Анализ_ИтогиНаСервере`;
- архивирование — группа открывается до построения очереди
  («Формирование очереди архива»), далее после каждого
  `Архив_ПодготовитьФайлНаСервере`;
- проверка архива — после каждого `Проверка_ПроверитьФайлНаСервере`;
- восстановление — после каждого `Восстановление_ВосстановитьНаСервере`;
- очистка — после каждого нового `Очистка_ОчиститьЗаписьНаСервере(Индекс)`.

Серверный вызов на запись остаётся коротким, поэтому индикатор успевает
перерисовываться между записями. `ОбработкаПрерыванияПользователя` не
добавляется: прерывание оставило бы частично очищенный сеанс, а безопасность
обеспечивается проверенным манифестом.

### Отметка «архивный»

Ставится в той же транзакции, что и очистка, **до** удаления содержимого.

- Версия (`Вид = "version"`): `ВерсииФайлов.ДатаПереносаВАрхив =
  ТекущаяДатаСеанса()`, `УсловноПеренесенВАрхив = Ложь`; запись через уже
  существующий `ЗаписатьОбъектСодержимогоФайла` (для исторической версии — с
  `КонвертацияФайлов`).
- Присоединённый файл в отдельном справочнике (`Вид = "file"`, справочник из
  `ИменаСправочниковПрисоединенныхФайлов`): менеджер записи
  `РегистрСведений.СведенияОФайлах` по `Файл`, `Прочитать()`, затем
  `ДатаПереносаВАрхив` и `УсловноПеренесенВАрхив = Ложь`, `Записать()`.
  Отсутствующая запись создаётся.
- `Справочник.Файлы` без версий: отметка невозможна (факт 8). Очистка
  разрешается, в лог и в строку результата пишется «Отметка архива недоступна:
  файл без версий». Это известное ограничение, а не ошибка.

Восстановление снимает отметку **до** записи содержимого и в той же транзакции:
`ДатаПереносаВАрхив = Дата(1,1,1)`, `УсловноПеренесенВАрхив = Ложь`. Порядок
обязателен: если содержимое уже записано, а отметка ещё стоит, БСП попытается
распаковать файл как zip (факт 1).

Повторная очистка уже очищенного файла отметку не меняет (запись «Уже очищено»
пропускается).

### Манифест

`formatVersion` остаётся `2`: поля не меняются по смыслу, добавлены только
`periodStart` и `periodEnd`. `configName` — имя новой обработки, поэтому
манифесты прежней сборки отклоняются с явным сообщением «манифест создан другой
обработкой». Решение согласовано.

### Изменения в исходной обработке

- удалить `Forms/ВсеФайлы` (XML и каталог);
- удалить `<Form>ВсеФайлы</Form>` из `СозданиеАрхиваДокументооборота.xml`;
- удалить группу `ГруппаВсеФайлы`, кнопку `КнопкаВсеФайлы`, команду `ВсеФайлы`
  и обработчик `ВсеФайлы` из формы «Основная»;
- `ФормаПрогресс`, `Основная`, `Настройка` и объектный модуль не меняются.

## Инварианты

1. Очищается только запись, для которой в манифесте есть строка с совпадающими
   размером и SHA-256, а манифест `completed = true`, `verified = true` и
   совпадает по `infobaseId` и `dataArea`.
2. Под блокировкой повторно проверяются тип хранения «В информационной базе»,
   владелец версии и хеш.
3. Одна запись — одна транзакция; ошибка записи не откатывает остальные.
4. После очистки содержимое пусто; после восстановления размер и хеш совпадают
   с манифестом.
5. Карточки, версии и связи сохраняются при любом исходе.
6. Очищено ⇒ помечено, кроме файлов без версий (журналируется).
7. Восстановлено ⇒ отметка снята.

## Проверки

Статические тесты `tests/test_archive_guards.py` переводятся на новый модуль;
добавляются проверки:

- отметка ставится до удаления содержимого и снимается до записи;
- `УсловноПеренесенВАрхив` нигде не выставляется в `Истина`;
- период применяется к трём запросам построения очереди и к анализу;
- при незаданном периоде запись без владельца и без даты всё равно попадает в
  очередь;
- операции по сеансу не используют период;
- поле периода не входит в `ГруппаПрогресса` и доступно до запуска операции;
- очистка вызывается по одной записи.

Сборка проверяется `epf-validate` и `form-validate`. Функциональный прогон —
на копии базы: архив → проверка → очистка (проверить отметку в форме версии и
сообщение при открытии) → восстановление (проверить, что файл открывается).
Дополнительно — файл, попавший в период, и файл вне периода.

## Риски

- **Сообщение при открытии очищенного файла** теперь «Файл находится в файловом
  архиве. Данные файла недоступны. Для получения файла обратитесь к
  администратору». Это ближе к правде, но упоминает файловый архив, которого
  нет. Приемлемо; альтернатива — не ставить штатную отметку.
- **Файлы в томах и внешних хранилищах** с нашей отметкой не встречаются: они в
  очередь не попадают.
- **Взаимоблокировки** с типовой записью файлов остаются возможными; добавляется
  блокировка `СведенияОФайлах`. Порядок: карточка/версия → `НаличиеФайлов` по объекту-владельцу → `СведенияОФайлах` →
  `ХранилищеФайлов`; он совпадает с порядком подписки БСП
  `ПриЗаписиПрисоединенногоФайлаСервер`, иначе возможна взаимоблокировка (ABBA).
  При взаимоблокировке платформа откатит одну транзакцию,
  обработка зафиксирует ошибку по записи, повтора нет.
- **Файлы без версий** остаются без отметки (факт 8).

## Что оставлено исполнителю

- Точные идентификаторы элементов формы и порядок групп.
- Разбиение `Очистка_ВыполнитьНаСервере` на `Очистка_ОчиститьЗаписьНаСервере`
  с сохранением текущей структуры транзакции и подсчёта итогов.
- Способ кеширования дат владельцев и точная форма запросов периода.
- Текст сообщений в лог.
