# Дизайн режима «Все присоединённые файлы»

Дата: 05.11.2026. Основание: план `docs/superpowers/plans/2026-11-05-all-attached-files.md`, инвентаризация и таблица совместимости.

> **Обновление 07.11.2026.** Режим вынесен из `СозданиеАрхиваДокументооборота.epf`
> в отдельную обработку
> `УправлениеАрхивомПрисоединенныхФайловОчисткаИВосстановление.epf`
> (дизайн — `docs/design/upravlenie-arhivom-faylov.md`). Исходная обработка
> сохранила только сценарий 1С-Отчётности; форма `ВсеФайлы`, её команда и
> кнопка удалены. Описание ниже сохраняет историю решения и остаётся верным по
> существу, кроме указанного примера `configName`: это имя **обработки**
> (`Метаданные.Имя`), а не имя конфигурации.

## Принятые решения

1. **Очистка** — очистка двоичного содержимого с сохранением карточки файла, версий и связей. Физическое удаление элементов и пометка удаления не используются.
2. **Архив** — внешний каталог сеанса с манифестом JSON, а не штатный файловый архив БСП: штатный механизм глобален и управляется регламентным заданием, выборочного «архивировать этот файл» в нём нет.
3. **Версии и подписи** — обрабатываются все версии файлов (опция «Только текущие версии» сужает объём). Электронные подписи и текстовое содержимое не изменяются.
4. **Совместимость со старыми архивами** — старый формат (`catalog.xml` + разложенные по каталогам файлы) остаётся в существующем сценарии 1С-Отчётности. Новый режим использует собственный формат сеанса и не читает старые архивы.
5. **Хранилища** — поддерживается только `ВИнформационнойБазе`: именно там очистка освобождает место в базе. Тома на диске и хранилища двоичных данных блокируются.

## Решение

Доработка выполняется внутри того же EPF отдельной формой `ВсеФайлы`, открываемой кнопкой из `Основная`. Существующий сценарий 1С-Отчётности не переписывается.

Смысл операций:

| Операция | Что делает | Что не делает |
|---|---|---|
| Анализ | Считает файлы/версии, объёмы и типы хранения | Не пишет на диск и в базу |
| Архивировать | Копирует содержимое в каталог сеанса, считает SHA-256, пишет манифест | Не меняет базу |
| Проверить | Читает архив и сверяет размеры/хеши с манифестом | Не меняет базу |
| Очистить | Для записей проверенного манифеста заменяет содержимое пустым, `Размер = 0`, карточка и связи сохраняются | Не удаляет элементы справочников, не трогает подписи и историю версий |
| Восстановить | Возвращает содержимое из архива в те же объекты/версии | Не создаёт новые версии, не перезаписывает изменённое содержимое |

Очистка и восстановление — отдельные команды с подтверждением. По умолчанию выполняется только анализ.

**Текущий статус (06.11.2026):** очистка и восстановление включены. Обе операции
работают с `РегистрСведений.ХранилищеФайлов`, выполняются в транзакции с
управляемыми блокировками и требуют проверенного манифеста, привязанного к
текущей базе и области данных. Конкурентное поведение и откаты ещё не
подтверждены двумя параллельными сеансами.

## Область данных

- `Справочник.Файлы` + все версии из `Справочник.ВерсииФайлов` (кроме помеченных на удаление), включая текущую;
- файлы без версий;
- все справочники, имя которых содержит `ПрисоединенныеФайлы` и есть реквизиты `ФайлХранилище`, `ТипХраненияФайла`, `ВладелецФайла`, `Размер` (включая справочники ЭДО, не перечисленные в жёсткой карте существующего режима).

В очередь включаются только записи с `ТипХраненияФайла = Перечисления.ТипыХраненияФайлов.ВИнформационнойБазе`: фильтр задан в запросах, а перед чтением содержимого тип проверяется повторно. Содержимое читается штатным механизмом БСП `РаботаСФайлами.ХранилищеФайлаИзИнформационнойБазы`, то есть из `РегистрСведений.ХранилищеФайлов` → `Справочник.ХранилищеДвоичныхДанных`; резервный путь — реквизит `ФайлХранилище` (старый способ хранения).

По выгрузкам конфигураций таких справочников 425 в `hlev` и 53 в `bgu`. Состав определяется динамически по `Метаданные.Справочники`, поэтому новые справочники присоединённых файлов подхватываются без изменения кода. Данные каждого справочника читаются отдельным запросом — это разные таблицы, объединить их в один запрос без потери сопровождаемости нельзя.

Опция «Только текущие версии» ограничивает обработку текущей версией каждого файла.

Не входят: произвольные двоичные реквизиты других объектов, вложения в томах/хранилищах двоичных данных, штатный файловый архив БСП.

## Формат архива

```
<КаталогАрхива>/
  Сеанс_20261105_120000/
    manifest.json
    files/
      <uuid-версии>.bin
      <uuid-файла>.bin
```

`manifest.json`:

```json
{
  "formatVersion": 2,
  "sessionId": "Сеанс_20261105_120000",
  "createdAt": "2026-11-05T12:00:00",
  "user": "...",
  "configName": "УправлениеАрхивомПрисоединенныхФайловОчисткаИВосстановление",
  "configVersion": "",
  "infobaseId": "8f0b...",
  "dataArea": 25,
  "completed": true,
  "verified": false,
  "records": [
    {
      "kind": "version",
      "catalog": "ВерсииФайлов",
      "refUuid": "...",
      "fileUuid": "...",
      "ownerType": "Документ.Поступление...",
      "ownerUuid": "...",
      "name": "Акт.pdf",
      "extension": "pdf",
      "number": "1",
      "size": 12345,
      "hash": "base64(sha256)",
      "relPath": "files/....bin",
      "storageType": "ВИнформационнойБазе"
    }
  ]
}
```

Правила:

- имена файлов внутри архива — только UUID, поэтому кириллица, пробелы и опасные имена не влияют на путь;
- `relPath` проверяется: только `files/`, без `..`, без абсолютных путей;
- хеш — SHA-256 в Base64;
- манифест после архивирования: `completed = true`, `verified = false`;
- `verified = true` выставляет только команда «Проверить архив» и только при нуле ошибок;
- очистка и восстановление требуют `completed = true` и `verified = true`;
- `formatVersion` должен быть равен 2; манифесты прежнего формата отклоняются;
- `infobaseId` и `dataArea` должны совпадать с текущим сеансом;
- при сбое до записи манифеста каталог сеанса помечается `manifest.incomplete.json` и не может быть очищен.

## Алгоритм архивирования

1. Проверить/создать каталог **на клиенте**, проверить запись пробным файлом.
2. На сервере сформировать очередь единиц (без двоичных данных) и шапку манифеста; на клиенте создать каталог сеанса и `files/`.
3. Для каждой единицы:
   - сервер проверяет `ТипХраненияФайла = ВИнформационнойБазе`, читает `ХранилищеЗначения`, считает SHA-256 и передаёт данные через временное хранилище; пустое содержимое пропускается;
   - клиент записывает `<uuid>.bin` в свой каталог и подтверждает запись серверу;
   - только подтверждённые записи попадают в манифест.
4. Клиент записывает `manifest.json` с `completed = true`, `verified = false`.
5. Ошибка записи файла или манифеста не позволяет очистку: в манифест попадают только успешно записанные файлы.

Отдельная команда «Проверить архив» заново читает все файлы сеанса **на клиенте**, передаёт их на сервер и сверяет размеры и SHA-256; при отсутствии ошибок манифест перезаписывается с `verified = true`.

## Алгоритм очистки

1. Клиент читает манифест, сервер проверяет `formatVersion`, `completed`, `verified`, `configName` (имя обработки), `infobaseId` и `dataArea`.
2. Клиент заново проверяет все файлы архива (существование, размер, SHA-256). При любой ошибке очистка отменяется целиком.
3. Для каждой записи на сервере:
   - открыть транзакцию;
   - поставить управляемые блокировки: версия/карточка присоединённого файла, карточка `Справочник.Файлы` для версии, запись `РегистрСведений.ХранилищеФайлов` по `Файл`;
   - найти объект по UUID; проверить владельца/файл для версии;
   - повторно проверить `ТипХраненияФайла = ВИнформационнойБазе`; при изменении — пропуск без записи;
   - прочитать текущее содержимое через `РаботаСФайлами.ХранилищеФайлаИзИнформационнойБазы`;
   - пусто → «уже очищено», пропуск;
   - хеш не равен манифесту → «содержимое изменилось», пропуск;
   - иначе `РегистрыСведений.ХранилищеФайлов.УдалитьДвоичныеДанные(Ссылка)`, очистить `ФайлХранилище`, `Размер = 0`, записать объект;
   - проверить, что содержимое пусто, обновить размер карточки текущего файла;
   - зафиксировать транзакцию. Любая ошибка — `ОтменитьТранзакцию()` и запись в результат со статусом «Ошибка».
4. Для исторической версии объект записывается с `ДополнительныеСвойства.Вставить("КонвертацияФайлов", Истина)`, чтобы подписка `ВерсииФайловПриЗаписи` не перенесла реквизиты исторической версии в карточку текущего файла.
5. Результат по каждой записи — в таблицу и лог.

## Алгоритм восстановления

1. Проверить манифест, имя конфигурации, `infobaseId`, `dataArea` и `verified`.
2. Для каждой записи проверить наличие файла, размер и SHA-256.
3. Открыть транзакцию и поставить те же блокировки, что при очистке.
4. Найти объект; для версии — проверить, что владелец совпадает с `fileUuid`.
5. Повторно проверить тип хранения; при изменении — ошибка без записи.
6. Текущее содержимое:
   - совпадает с архивом → «уже восстановлено», пропуск;
   - непустое и отличается → конфликт, пропуск без перезаписи;
   - пустое → `РегистрыСведений.ХранилищеФайлов.ЗаписатьДвоичныеДанные`, очистить `ФайлХранилище`, установить исходный `Размер`, записать объект;
7. Прочитать содержимое повторно и сверить SHA-256; при расхождении — исключение и откат.
8. Зафиксировать транзакцию. Повторный запуск идемпотентен.

## Отказоустойчивость

- Архив пишется до очистки; очистка без проверенного манифеста запрещена.
- Проверка хеша выполняется и при архивировании, и перед очисткой, и при восстановлении.
- Частичный сбой не оставляет «полуготовый» манифест.
- Транзакция базы не удерживается на время записи файлов: сначала внешний архив, затем короткие транзакции по одной записи.
- Очистка и восстановление каждой записи атомарны: запись регистра, карточка/версия и размер меняются в одной транзакции; при ошибке выполняется откат.
- Одинаковые хеши разных файлов не считаются ошибкой (дедупликация в архиве не выполняется — приоритет безопасности).

## Интерфейс формы

Реквизиты: `КаталогАрхива`, `Сеанс`, `ТолькоТекущиеВерсии`, `ТаблицаРезультата`, `ТекстЛога`.  
Команды: `Анализ`, `Архивировать`, `ПроверитьАрхив`, `Очистить`, `Восстановить`, `ПоследнийСеанс`.

Каталог архива — путь **на компьютере пользователя** (клиенте 1С), как и в существующем сценарии 1С-Отчётности. Создание каталогов, запись и чтение файлов архива выполняются на клиенте; сервер только читает/записывает базу, считает хеши и формирует манифест. Двоичные данные передаются между клиентом и сервером через временное хранилище по одному файлу, поэтому большой архив не требует большой памяти за один вызов.

Используются те же клиентские файловые методы, что и в исходной обработке (`Новый ДвоичныеДанные(путь)`, `Данные.Записать(путь)`, `СоздатьКаталог`, `НайтиФайлы`, `УдалитьФайлы`). **Хеширование выполняется только на сервере**: `ХешированиеДанных` на клиенте недоступен, поэтому при проверке и восстановлении файл передаётся на сервер через временное хранилище. Веб-клиент не поддерживается, как и в исходном сценарии.

## Безопасность

- нет физического удаления элементов и версий;
- нет записи SQL;
- неподдерживаемые типы хранения только репортируются;
- конфигурация-источник фиксируется в манифесте;
- очистка и восстановление требуют явного подтверждения;
- секреты и строки соединения в манифест не пишутся.

## Что не проверено

- Сквозной цикл на большом объёме и на данных `hlev` (всего один файл). В `bgu`, область 25, цикл на двух файлах выполнен.
- Конкурентные сценарии двумя сеансами: порядок блокировок обработки не совпадает с порядком `ЗаписатьДвоичныеДанные` (сначала `ХранилищеДвоичныхДанных` по хешу). Возможна взаимоблокировка; платформа откатывает одну транзакцию, обработка фиксирует ошибку по записи. Потери данных не ожидается, но автоматического повтора нет.
- Работа в клиент-серверном режиме: архив пишется на клиенте, поэтому достаточно доступного пользователю каталога; на стенде проверен файловый режим.
- Поведение всех подписок конкретных конфигураций при прямой записи очищенного/восстановленного объекта, кроме `ВерсииФайловПриЗаписи` и регистрации обменов.

Эти пункты отражены в `tests/acceptance-matrix.md` как «не проверено».
