Статус: подготовлен 06.11.2026; первый прогон выполнен в `bgu`, область 25.
Для повторных изменяющих проверок использовать **копию** информационной базы;
рабочую базу не изменять.

> присоединённые файлы» тогда жил внутри `СозданиеАрхиваДокументооборота.epf`
> отдельной формой `ВсеФайлы`. Сейчас режим вынесен в
> `УправлениеАрхивомПрисоединенныхФайловОчисткаИВосстановление.epf`

> «архивный») — `docs/testing/upravlenie-arhivom-acceptance.md`.

## Что проверяется

1. Очистка удаляет двоичные данные из `РегистрСведений.ХранилищеФайлов` и не
   трогает карточки, версии и связи.
2. Восстановление возвращает те же байты (SHA-256) в тот же объект/версию.
3. Манифест другой базы или другой области данных отклоняется **до первой
   записи**.
4. Неполный или непроверенный архив не допускает очистку.
5. Ошибка в середине операции откатывает запись регистра и карточки.
6. Конкурентная запись не приводит к потере нового содержимого.

## Подготовка

- Копия `bgu` с включённым разделением данных, сеанс в области `25`.
- Не менее двух файлов с содержимым, физически хранящимся в ИБ:
  - текущая версия файла;
  - историческая (не текущая) версия того же или другого файла.
  Найти их можно запросом:

  ```bsl
  ВЫБРАТЬ ПЕРВЫЕ 10
      Версии.Ссылка,
      Версии.Владелец,
      Версии.НомерВерсии,
      Версии.Размер,
      Версии.ТипХраненияФайла
  ИЗ
      Справочник.ВерсииФайлов КАК Версии
  ГДЕ
      Версии.ТипХраненияФайла = ЗНАЧЕНИЕ(Перечисление.ТипыХраненияФайлов.ВИнформационнойБазе)
      И Версии.Размер > 0
      И НЕ Версии.ПометкаУдаления
  ```

- Записать исходные значения: ссылки, номера версий, размеры, SHA-256
  содержимого (можно получить через `РаботаСФайлами.ХранилищеФайлаИзИнформационнойБазы`
  в отладке или сверить после восстановления).
- Свободный каталог на клиенте для архива.

## Основной сценарий

1. Открыть `СозданиеАрхиваДокументооборота.epf` → **«Все присоединенные файлы»**.
   (С 07.11.2026 — открыть `УправлениеАрхивомПрисоединенныхФайловОчисткаИВосстановление.epf`:
   режим вынесен в отдельную обработку, кнопка в исходной удалена.)
2. Указать каталог архива → **«Проверить каталог»**.
3. **«Анализ»** — убедиться, что в очереди только записи
   «ВИнформационнойБазе», объём совпадает с ожидаемым.
4. **«Архивировать»** — дождаться манифеста. Проверить в `manifest.json`:
   - `formatVersion = 2`;
   - `infobaseId` не пуст;
   - `dataArea = 25`;
   - `completed = true`, `verified = false`.
5. **«Проверить архив»** — `verified` должен стать `true`, ошибок нет.
6. Зафиксировать в базе до очистки:
   - `Справочник.Файлы.Размер` и `ТекущаяВерсия`;
   - наличие записей `РегистрСведений.ХранилищеФайлов` по выбранным ссылкам.
7. **«Очистить содержимое»** → подтвердить. Ожидаемый результат:
   - по каждой записи статус «Очищено»;
   - запись `ХранилищеФайлов` отсутствует;
   - `Справочник.Файлы.Размер = 0` для текущей версии;
   - карточка, версии, владелец и связи не изменились.
8. Повторить очистку — ожидается «Очищено: 0, пропущено: N» (идемпотентность).
9. **«Восстановить»** → ожидается «Восстановлено» по всем записям.
10. Сверить SHA-256 содержимого с исходным; `Размер` карточки вернулся к
    исходному.
11. Повторить восстановление — «Восстановлено: 0, пропущено: N».
12. Изменить содержимое одного файла и снова выполнить восстановление —
    ожидается «Конфликт», новое содержимое не перезаписано.

## Негативные проверки

| Проверка | Действие | Ожидание |
|---|---|---|
| Чужая область | В копии `manifest.json` заменить `dataArea` на `24` | Отказ загрузки/изменения до первой записи, содержимое в ИБ не меняется |
| Чужой `infobaseId` | Заменить `infobaseId` на случайный UUID | Отказ до первой записи |
| Непроверенный архив | Оставить `verified = false` | «Сеанс архива не проверен», очистка не начинается |
| Повреждённый файл архива | Изменить один байт в `files/*.bin` | Повторная проверка перед очисткой отменяет операцию целиком |
| Удалённый файл архива | Удалить один `.bin` | Очистка отменяется, частичных изменений нет |
| Ошибка записи | Смоделировать отказ (например, запрет записи регистра) | Транзакция откатывается, содержимое и размер прежние |

## Конкурентность (два сеанса)

1. Сеанс A выполняет очистку записи; сеанс B одновременно записывает новую
   версию/содержимое того же файла через типовую форму.
2. Допустимые исходы:
   - A ждёт блокировку, затем видит новый хеш и пропускает запись
     («содержимое изменилось»);
   - либо одна из транзакций откатывается по взаимоблокировке, вторая
     завершается; новое содержимое B сохраняется.
3. Недопустимо: новое содержимое B потеряно; карточка и версия рассинхронизированы;
   в регистре осталась «половина» записи.

Повторить для восстановления.

## Критерии остановки

Испытание немедленно прекращается, если:

- содержимое исчезло, а манифест не содержит нужной записи;
- после отката размер или содержимое отличаются от исходных;
- очистка затронула запись, которой нет в манифесте;
- манифест с чужим `dataArea`/`infobaseId` прошёл проверку.

Результат каждой проверки записывать в `tests/acceptance-matrix.md`.
